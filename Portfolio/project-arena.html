A.R.E.N.A

A Team-Based Arena Game - 2 months project

Unreal Engine 5 C++ & Blueprints Multiplayer / Networking Epic Online Services (EOS) Gameplay Ability System (GAS) UMG / UI

Project Overview

This project is a team-based multiplayer combat game focusing on robust networking, dynamic UI, and ability-driven combat using Unreal Engine's Gameplay Ability System (GAS). Initially developed using Steam matchmaking, the project was later migrated to Epic Online Services (EOS) to overcome Steam's AppID testing limitations.

Core Technical Implementation

Networking & The "TeamID" Challenge

One of the biggest hurdles was managing team assignments across different multiplayer sessions. In our lobby system, players join a host, and the host's Unique Net ID becomes the TeamID. When two teams find a match, they are merged into a new match session. This transition caused players to lose their original TeamIDs.

To solve this, I designed a robust replication flow:

  • GameInstance: Stores the TeamID locally so it survives session transitions.
  • PlayerController: On BeginPlay, it commands the GameMode to spawn the character chosen in the lobby.
  • PlayerState: Once initialized, the client pulls the TeamID from their GameInstance and sends a Server RPC to update the Server's version of the PlayerState.
  • RepNotify: The Server replicates this data back down to all clients, triggering an OnRep function that allows clients to locally reconstruct a Map mapping TeamIDs to arrays of PlayerStates.

Dynamic UI Systems (UMG)

I built a comprehensive UI framework that responds to network events, including overhead nameplates, party frames, and scoreboards:

  • Overhead Healthbars & Castbars: Replicated over the network. Opacity fades if line of sight is broken or if the target is too far away. Friendly healthbars are colored green, while enemy bars are red, calculated by comparing TeamIDs.
  • Party & Enemy Frames: Automatically generated on the side of the screen when players are added to a team. They subscribe to OnHealthUpdated and OnCastStarted events directly from the characters.
  • Scoreboard: Tracks Damage Done and Kills. Kills are awarded via a payload sent to OnHealthChanged just before a target dies.

Gameplay Mechanics & Controls

To mimic traditional MMORPG/Arena controls (like World of Warcraft), I modified the input handling so that:

  • Holding Right-Click rotates both the camera and the character.
  • Holding Left-Click rotates only the camera without affecting the character's facing direction.
  • Holding Both Mouse Buttons moves the character forward.
  • Added smooth camera interpolation for zooming in and out.

Gameplay Ability System (GAS) & Combat

I utilized GAS for all combat logic. A key feature was implementing critical hits and team-based damage validation:

  • Damage Validation: A "Should Skip Hit" custom node ensures players cannot damage their own teammates by validating TeamIDs before applying Gameplay Effects.
  • Critical Hits: Handled in a custom GameplayEffectExecutionCalculation (GEEC). I implemented a 20% chance to score a critical hit, resulting in 50% extra damage. This flags the execution data, which the AttributeSet reads to display red, floating damage numbers for crits, and yellow for normal hits.

Key Challenges Overcome

⏱️ Network Timing & Race Conditions:

Order of operations across a network is unpredictable. Trying to access PlayerState or GameState on a client before it was fully replicated caused crashes or empty UI frames. I solved this by implementing robust retry-logic and tying UI generation strictly to OnRep notifies rather than local BeginPlay events.

📦 Lobby Resource Management:

Loading full combat characters in the lobby was resource-heavy. I created a lightweight "Mannequin" lobby character that pulls visual data (Skeletal Mesh, AnimBP, Materials) from a DataTable, saving memory and load times.

🔌 Steam AppID Restrictions:

Steam's default AppID (480) stopped broadcasting available sessions reliably, making testing impossible. I made the executive decision to migrate the entire project's matchmaking backend over to Epic Online Services (EOS), which restored our ability to test over the internet.

My Role

As a core programmer on this project, I took responsibility for the networking backbone, UI architecture, and gameplay systems integration. My main contributions included:

  • Multiplayer & Network Engineering: I handled the matchmaking flow, migrating the project from Steam to Epic Online Services (EOS). I engineered the replication logic for PlayerState variables, ensuring custom data like TeamID persisted flawlessly across server transitions from the lobby to the active match.
  • UI/UX & UMG Framework: I built the entire dynamic UI system from the ground up. This included WoW-style party and enemy frames that dynamically generate based on replicated network data, overhead nameplates with line-of-sight opacity, floating damage numbers, and a fully functional end-of-match scoreboard.
  • Combat & Gameplay Ability System (GAS): I integrated custom execution calculations within GAS to handle critical hits and friendly fire prevention. I also developed the WoW-style camera and movement controls, allowing for independent camera rotation and dual-mouse-button movement.
  • Project Architecture & Optimization: I took the initiative to refactor our C++ and Blueprint folder structures for better scalability. Additionally, I optimized the lobby system by creating a "Mannequin" actor driven by a DataTable, bypassing the need to load heavy, combat-ready characters before the match started.

Challenges and Learning Outcomes

Working on a multiplayer game of this scale introduced several complex problems that deeply improved my understanding of Unreal Engine's networking framework:

  • Network Order of Operations: The biggest recurring challenge was race conditions. I learned firsthand that you cannot rely on local BeginPlay events for multiplayer UI or logic. Data takes time to travel, and I had to master the use of OnRep functions and safe-retry logic to ensure PlayerState and GameState were fully initialized on clients before attempting to construct UI elements like Party Frames.
  • Data Persistence Across Sessions: Unreal Engine destroys most actors when transitioning between levels or sessions. Learning how to leverage persistent local classes like the GameInstance to temporarily hold data (like Team IDs) and re-inject it into the Server upon connecting to a new map was a major breakthrough.
  • Blueprint vs C++ Replication Quirks: I learned how to navigate engine-specific limitations, such as the inability to replicate Maps or Sets directly. I solved this by reconstructing the data locally on clients using replicated Structs. I also learned that C++ ReplicatedUsing (RepNotify) variables do not automatically trigger their functions on the Server, requiring manual calls to keep host/client logic synchronized.
  • Agile Problem Solving: When Steam's default AppID 480 stopped broadcasting our sessions, development came to a halt. Deciding to rapidly pivot the entire backend to Epic Online Services taught me how to stay adaptable and implement third-party SDKs under pressure.

Conclusion

This project was an incredible deep dive into the complexities of multiplayer game development in Unreal Engine 5. By tackling severe race conditions, migrating networking backends mid-development, and successfully merging UI with the Gameplay Ability System, I gained a profound appreciation for robust, scalable network architecture.

The challenges I faced with state replication and session management have given me a solid, practical foundation in multiplayer programming, skills that I now carry forward into every system I architect.
