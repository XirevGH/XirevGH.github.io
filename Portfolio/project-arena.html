A.R.E.N.A

Networked Sci-Fi Arena Fighter - 7 Week Team Project

Role: Lead Gameplay & Network Programmer Team Size: 5 Time: 7 Weeks Unreal Engine 5 C++ Gameplay Ability System (GAS) Networked Multiplayer
View Source Code on GitHub

Game Overview

Developed over 7 weeks in Unreal Engine 5 (C++ and Blueprints) as a 5-person team project, A.R.E.N.A is a competitive sci-fi hero arena fighter featuring 1v1, 2v2, and 3v3 team deathmatches. Inspired by MMORPG arena combat, the game emphasizes low-latency networked replication, MMO-style dual-mouse movement, real-time overhead UI feedback, and modular ability combat driven by the Gameplay Ability System (GAS).

Core Technical Implementation

1. Session-Persistent Team Replication & Custom Replicated Structs

When transitioning from pre-match lobbies into dedicated match sessions, Unreal Engine destroys player actors, wiping session identifiers. To preserve team identity and resolve Unreal's network replication limits, a multi-tier replication pipeline was engineered:

  • GameInstance Handoff: When a lobby matches teams, player controllers store their host-assigned TeamID locally in the GameInstance, bridging data across level transitions.
  • Replication of Nested Collections via Wrapper Structs: Because Unreal Engine cannot natively replicate TMap collections or nested arrays, custom replicated USTRUCT() containers (S_PlayerStateTeams) were engineered to map string team IDs to arrays of PlayerState pointers across the network.
  • C++ RepNotify Server Synchronization: In C++, ReplicatedUsing callback functions (such as OnRep_TeamID) do not trigger automatically on the server/host. The authority pipeline explicitly calls these callbacks server-side on assignment, ensuring client and host team maps remain strictly synchronized.

2. Gameplay Ability System (GAS), Friendly Fire & Critical Hits

All combat abilities, cooldowns, and damage calculations are implemented through Unreal Engine's Gameplay Ability System (GAS):

  • Centralized Enum Keybinding (`EAbilityInputID`): Mapped input actions directly to GAS ability triggers using a custom byte enum, allowing Enhanced Input contexts to activate abilities cleanly.
  • Team-Based Friendly Fire Filtering: Created custom validation logic (ShouldSkipHit) on ability actors, comparing caster and target PlayerState team IDs to prevent damage, debuffs, or collision overlap on allies.
  • Critical Hit Execution & Attribute Callbacks: In CharacterAttributeSet.cpp (PostGameplayEffectExecute), critical hits are calculated with a 20% probability for 1.5x damage. The outcome is packaged into a payload sent to the character, dynamically triggering yellow (normal) or red (critical) floating damage indicators.

3. Dynamic Replicated UI (UMG) & Consecutive Cast Synchronization

I engineered a networked UI framework that reacts in real time to game state changes, including overhead nameplates, party frames, cast bars, and scoreboards:

  • Line-of-Sight Overhead Nameplates: Overhead nameplates query the target's PlayerState for team affiliation (Green for friendly, Red for enemy). Nameplate opacity dynamically fades based on camera distance and line-of-sight raycasts.
  • Consecutive Cast Notification Hack (`S_CastInfo`): When players cast the same spell repeatedly, identical replicated variables would fail to trigger OnRep on clients because the data had not changed. To solve this, a custom struct (S_CastInfo) was built with an auto-incrementing integer timestamp, forcing network dirtiness and ensuring every cast bar triggers reliably.
  • Dynamic Party & Enemy Frames: Party frames construct dynamically from replicated GameState player arrays, subscribing to live health and cast delegates with safe fallback handling for late-connecting clients.
  • End-of-Match Scoreboard & Rematch Voting: Replicated scoreboard entries track kills and damage, exposing player states directly on spawn. When the match concludes, a voting loop tallies player votes in GameState and returns the party to the lobby.

4. Memory-Optimized Lobby Architecture & DataTable Mannequins

Loading heavy, combat-ready character Blueprints with full Gameplay Ability System components inside pre-match lobbies caused excessive memory usage and prolonged load times:

  • Lightweight Lobby Mannequins: Created a dedicated preview character (BP_LobbyMannequin) that completely bypasses GAS initialization.
  • DataTable-Driven Mesh Swapping: Preview characters query a DataTable (DT_CharacterLobbyData) to dynamically load skeletal meshes, material parameters, and lobby idle animations without allocating combat memory.
  • Match Start Countdown Gates: Synchronized arena barrier gates (BP_StartGate) that open across all clients when preparation timers elapse.

5. MMO-Style Controls, Ground Decal Targeting & Debug Tooling

To deliver responsive, PC-arena controls, custom input mapping and targeting tools were implemented:

  • Dual-Mouse Navigation: Holding Right-Click rotates both character and camera; holding Left-Click orbits the camera independently; holding Both Mouse Buttons drives movement forward.
  • Ground Decal Reticle Targeting (`BP_Cast_AOE`): Ground-targeted abilities project a cursor-snapping decal reticle with cancel recovery logic, keeping the indicator anchored under the mouse until cast confirmation.
  • In-Game Developer Debug Menu (`WBP_DeveloperOptions`): Created an in-game developer panel allowing instant runtime modification of TeamID and team arrays for rapid local testing without re-launching multiple game instances.

Key Challenges Overcome

Replicating Complex Collections Across Sessions:

Unreal Engine cannot replicate TMap collections or nested arrays natively, and level transitions wipe player state data. Wrapping arrays into custom replicated USTRUCT() containers (S_PlayerStateTeams) and caching team IDs in the local GameInstance enabled seamless team reconstruction across match servers.

Consecutive Identical Casts Failing to Trigger OnRep:

Casting the exact same spell twice in a row caused Unreal's replication system to skip sending updates because variable values were identical. Embedding an incremental integer timestamp into the replicated struct (S_CastInfo) forced property dirtiness, guaranteeing cast bars update reliably every single cast.

C++ RepNotify Server/Host Desynchronization:

Unlike Blueprints, C++ ReplicatedUsing callback functions do not automatically execute on the server when modified. Explicitly invoking the OnRep callback server-side during property assignment ensured host and client team logic remained in parity.

Steam AppID Restrictions & Session Broadcasting:

Steam's default testing AppID (480) stopped broadcasting available sessions reliably, halting multiplayer testing. Migrating the project matchmaking backend over to Epic Online Services (EOS) restored reliable worldwide session discovery.

Project Outcome

Delivered over the 7-week development cycle, the game achieved:

  • A complete 1v1, 2v2, and 3v3 arena combat framework with low-latency replication in C++
  • Full Gameplay Ability System (GAS) integration with team filtering and critical hit calculations
  • Dynamic, replicated overhead nameplates, cast bars, party frames, and scoreboard UI
