Othello AI & Visualizer

A High-Performance AI & Algorithmic State Visualizer - 2 Week Solo Project

Role: Solo Developer Time: 2 Weeks Java 64-Bit Bitboard Minimax & Alpha-Beta Pruning Algorithmic Visualizer
View Source Code on GitHub

Project Overview

Originally conceived during a university course on algorithms and data structures, this project evolved from a simple console application into a high-performance Othello (Reversi) AI benchmark and interactive state visualizer written in Java.

To explore the real-world performance differences between memory layout paradigms and tree search algorithms, four separate board representations were developed from scratch and evaluated across millions of board states: 2D Cell Objects, 2D Primitives, 1D Flat Array, and 64-Bit Parallel Bitboards. Through Alpha-Beta pruning and heuristic move ordering, the final Bitboard engine achieved a 2.68 million times speedup over the naive baseline.

Core Technical Implementation

1. Four Memory Architecture Paradigms

The project systematically tests how memory layout and pointer overhead directly impact search throughput during deep recursive minimax evaluation:

  • Engine 1 (2D Cell Objects): Models the 8x8 board as an array of object references (Cell[][]). Naively iterates over all 64 coordinates and checks all 8 directions from scratch.
  • Engine 2 (2D Primitive Values): Replaces heap-allocated Cell objects with a contiguous primitive integer array (int[][]), searching strictly for opponent pieces first before evaluating adjacent spaces.
  • Engine 3 (1D Flat Array): Compresses the board into a single 64-index primitive array (int[]). Implements line-scanning that tests opposite directions simultaneously and skips previously processed paths.
  • Engine 4 (64-Bit Parallel Bitboards): Eliminates array structures entirely. The entire board state is represented as two 64-bit integers (Java long), processing directional queries across all 64 tiles simultaneously using parallel bitwise math.

2. 64-Bit Branchless Bitboard Move Generation

By storing disc locations as binary bitmasks, valid moves and disc flips in any of the 8 directions are calculated simultaneously using bitwise shifts (e.g. << 1 for East, >> 8 for North) and logical masks:

  • Parallel Directional Propagation: A single bit shift shifts every friendly piece on the board into its adjacent neighbor in that direction.
  • Opponent Masking & Chain Extension: Bitwise AND operations with the opponent mask identify contiguous lines of enemy discs in one CPU cycle, propagating the ray until hitting an empty boundary cell.
  • Zero Branching Overhead: Completely eliminates nested coordinate loops and boundary checking conditions from the search core.

3. Search Optimizations: Minimax, Alpha-Beta & Move Ordering

To manage the combinatorial explosion of the Othello search tree, two foundational search optimizations were integrated:

  • Alpha-Beta Pruning: Prunes branches proven to produce sub-optimal outcomes, discarding vast subtrees without evaluating leaf nodes. At depth 15, this prunes 99.993% of the 2.8 trillion possible board states.
  • Heuristic Move Ordering (Insertion Sort): Alpha-Beta pruning is only as effective as the order in which moves are evaluated. Using a stable Insertion Sort driven by a positional static weight table, the engine explores the most promising candidate moves first, maximizing early alpha-beta cutoffs.
  • Stack-Allocated Backtracking: Shared primitive arrays write flips directly to the active board state and log changes to a pre-allocated undo stack, ensuring zero heap allocations per search node during deep recursive sweeps.

Key Benchmark Findings:

  • Exhaustive Throughput: At depth 9 without pruning, the 64-bit Bitboard engine evaluated all 7.0M states in 1.74 seconds (over 4.03 million states/s), outperforming the baseline 2D Cell Object engine by over 10.8x purely through memory locality and parallel bit shifts.
  • Pruning Efficiency: The full theoretical search tree at depth 15 encompasses approximately 2.78 trillion states (estimated ~87 days for the unoptimized baseline). Enabling Alpha-Beta Pruning with Heuristic Move Ordering reduced the required search space to just 9.5 million states (searching only 0.00034% of the tree).
  • Combined 2.68 Million Times Speedup: Combining bitwise parallel move generation with optimal branch pruning brought depth-15 search times down to 2.80 seconds, representing an overall 2.68 million times speedup over the naive exhaustive baseline.

Why Search Depth Scales Exponentially

In turn-based games like Othello, search complexity does not grow additively. With an average branching factor of ~6–10 valid moves per turn, each additional ply of depth multiplies the total search tree:

  • Depth 9: ~7.0 million possible game states
  • Depth 10: ~60 million game states (8.6× larger than Depth 9)
  • Depth 15: ~2.78 TRILLION game states (~400,000× larger than Depth 9)

Without algorithmic pruning, evaluating Depth 15 would take over 87 continuous days of computing. Searching it in 2.80 seconds represents cutting out 99.9996% of irrelevant branches while still finding the mathematically optimal move.

Key Challenges Overcome

Thread Safety & UI Progress Ticking:

Running depth-15 minimax searches freezes the main UI thread. I implemented a decoupled thread architecture using a dedicated SwingWorker thread. To keep the live UI node progress counter ticking smoothly, the counter was wrapped in a shared volatile, thread-safe memory state, allowing the UI thread to read live metrics while the background thread computes in isolation.

Cache Misses & Memory Alignment:

Object pointer dereferencing in complex nested nodes created immense CPU cache misses. By compressing OO search variables into tight, contiguous primitive arrays, the entire 8x8 game block fits perfectly inside a single L1 Cache line (64 ints = 256 bytes), achieving instant memory reads and bypassing slow RAM lookups.

Visualizer Reference Aliasing:

An elusive bug caused evaluated search targets to retrospectively show up as Valid or Invalid in early visualizer frames before they were ever evaluated. This was caused by 2D array pointer aliasing where working state references leaked into previous visualizer states. Completely resolved this by implementing strict deep-copy setters inside the visualization state machine.

Project Outcome

Delivered as a standalone high-performance Java engine, the project achieved:

  • An ultra-fast 64-bit parallel Bitboard move generator operating at over 4 million states per second
  • A complete Minimax AI with Alpha-Beta pruning and heuristic move ordering achieving a 2.68M speedup
  • A frame-by-frame algorithmic visualizer exposing search mechanics and bit-shifting operations graphically
