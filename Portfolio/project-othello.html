Project Overview

This project is a high-performance Othello (Reversi) Game & AI State Visualizer designed to compare and contrast two fundamentally different software architecture patterns: Object-Oriented frontier modeling and 64-bit Bitboard math [1].

Beyond standard gameplay, the system includes a frame-by-frame algorithmic visualizer. This debug-overlay system visually traces the sequential array scans, frontier expansions, recursive opponent chains, and 64-bit parallel shifts occurring inside the execution stack of both engines [1].

Core Technical Implementation

64-Bit Parallel Bitboards

Rather than representing the $8 \times 8$ board as an array of objects or integers, the Bitboard engine models the entire state as two 64-bit unsigned integers (unsigned long in C++, or long in Java) [4]. Each bit represents one cell on the board [4].

This enables the engine to calculate valid moves and flip discs across all 64 spaces simultaneously using bitwise shift operators (e.g., << 1 for East, >> 8 for North) [4] and parallel logical operations [4], completely bypassing the nested coordinate traversal loops required in traditional game loops [1].

Object-Oriented Frontier Expansion

To serve as a comparative benchmark, the Object-Oriented engine models the board as a flat 64-element primitive array [1]. Instead of iterating $0 \dots 63$ redundantly [1], it implements a localized **Frontier Expansion Search**:

  • Discs Scanning: It scans the board looking strictly for the opponent's active discs [1].
  • Radial Traversal: When an opponent disc is located, it scans radially outwards in all 8 directions to identify empty adjacent neighbor cells [1].
  • Direct Validation: It targets only those discovered empty neighbors, evaluating their line paths on the fly [1]. This minimizes the search space from 64 slots down to a tiny, active boundary frontier [1].

Backtracking & Garbage Collection Optimizations

During deep recursive tree searches, allocating and de-allocating memory objects in Java triggers frequent, unpredictable garbage collection (GC) pauses [3]. To solve this, the OO engine utilizes an optimized **stack-allocated undo array** [1, 2]:

  • No Object Allocations: A single, flat board array is shared across the entire depth of the minimax search tree [1, 2].
  • Pre-Allocated Undo Stack: At each search depth, the engine writes disc flips directly to the active board, logging the coordinates inside a pre-allocated `UndoState` stack [1, 2].
  • Backtracking: Upon completing a branch evaluation, the engine unwinds the stack to restore the board to its exact previous configuration [1, 2]. This enables thousands of deep-ply simulations with **zero object allocations** per node, avoiding GC overhead [2, 3].

Key Challenges Overcome

🔒 Thread Safety & UI Progress Ticking:

Running depth-15 minimax searches freezes the main UI thread. I implemented a robust, decoupled thread architecture using a dedicated SwingWorker thread. To keep the live UI node progress counter ticking smoothly, I wrapped the node counter in a shared volatile, thread-safe memory state, allowing the UI thread to read live metrics while the background thread computes in isolation.

⚡ Cache Misses & Memory Alignment:

Object pointer dereferencing in complex nested nodes creates immense CPU cache misses. By aligning all OO search variables into tight, contiguous primitive arrays, the entire 8x8 game block fits perfectly inside a single L1 Cache line (64 ints = 256 bytes), achieving instant memory reads and bypassing slow RAM lookups.

🐜 Visualizer Reference Aliasing:

An elusive bug caused evaluated search targets to retrospectively show up as "Valid" or "Invalid" in early visualizer frames before they were ever evaluated. I identified the cause as 2D array pointer aliasing (the working state array reference was leaking into previous visualizer states). I completely resolved this by implementing strict deep-copy setters inside our visualization framing state, maintaining perfectly isolated frames.

Challenges and Learning Outcomes

Developing this system offered deep insights into low-level memory performance, thread handling, and high-performance algorithms:

  • Bit-Level Thinking: Building custom bitwise algorithms taught me how to compress complex board queries into branchless, parallel CPU math [4].
  • Garbage Collection Mitigation: I mastered memory recycling techniques and pre-allocated stacks, allowing high-ply recursive game engines to execute with a flat memory footprint [2, 3].
  • Visual Debugging: Designing the algorithmic debugger proved that exposing a complex system's inner variables graphically is the single most effective way to locate and correct edge-case bugs.
